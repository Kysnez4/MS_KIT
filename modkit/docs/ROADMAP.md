## 1. Что уже есть (инвентарь)

| Возможность | API | Статус на телефоне |
|---|---|---|
| Хуки до/после/замена метода игры | `ctx.Before/After/Replace` (Harmony) | работает; на итераторах корутин тоже (`C_Battle_AllyUnit+_Play_X_d__N`.`MoveNext`) |
| События игры | `ctx.Events.On("battleStart"/"battleEnd"/"areaChange"/"enemySpawn"/"enemyDeath"/"bossSpawn"/"mainMenu")`, типизированные события | battleStart, enemyDeath использовались; остальные не проверены в этой сессии |
| Правка данных | `Data.For(ctx)`: `Edit`, `AddArtifact(s)`, `AddCombo`, `AddSynergy`, `EditSpell/GetSpell/ScaleSpell`, `AddClass` (экспериментально, ломает меню — не использовать) | артефакт/синергия/комбинация добавлялись; `EditSpell` проверен |
| Эффекты | `IEffects.Define`, `SetGlobalEffects`, `UseBuiltinEffects` (10001–10004), `OnHeroPass` | подстановка эффектов игры работает («Проклятия и дары»); `class_menu` использует `SetGlobalEffects` |
| Заклинания | `ISpells`: `Level`, `CanCast`, `SetAuto`, `Cast`, `Cooldown`, `InBattle`, `Paused`, `AddActive(ActiveSpellDef)` | проверено на Огненном шаре; Молния/Метеорит — нет |
| UI | `UiKit`: `OpenChecklist`, `OpenNumberForm`, `AddButton`, `Label`, `Picture` (PNG из zip), `PanView` (карта), `Pager` (стрелки), `AddHudButton` (кнопка в бою), `GameSprite` (спрайт игры), `OpenPage` | карта и Pager проверены; HudButton проверен; `GameSprite` не проверен |
| Реестры и библиотеки | `ctx.Registry<T>`, `ctx.Expose/Mod<T>`, `"library": true`, зависимости | работает; реестр `classes` (`CustomClass`) используется `class_menu` |
| Защита | `ctx.Guard/Error/Mark`, автоотключение при 5 ошибках за 10 с, журнал вылетов | работает |
| Тест без рук | мод `autotest` + `tools/autotest.py`, журнал `gamelog` | работает (бот ходит в бою, берёт заклинания и артефакты) |
| Классы | `class_menu` 2.1: карта всех 24 классов игры и классов модов, выбор записью `SelectClassID` | карта собрана, на телефоне ещё не проверена |

Граница возможностей (из практики): эффекты через подмену слотов покрывают **только характеристики**; условные, событийные и активные эффекты делаются своим кодом. Прокачка класса и строки таблицы `Class` для новых ID не работают (см. CLASSES.md §7). Заклинания спутников, духов и щита режутся только после пересчёта (число читается в `ApplySatelliteGroup`).

## 2. Принципы работы

1. **Проверка без экрана.** Любой мод должен писать в `modkit.log` строки «что включилось / что применено» с конкретными числами; для бойцов — через `gamelog` или `autotest` (см. MELONLOADER.md §11, §13). Нельзя писать в отчёте «работает», если не было строки лога или запуска `autotest`.
2. **Честно помечать непроверенное** (в `description`, в docs и в отчёте): «собрано, на устройстве не проверено».
3. **Версии.** Каждое изменение мода — повышение `version` в `mod.json` и в `ModDef` (иначе «+» не заменит старый zip). Изменение ядра `ModKit.dll` требует полного перезапуска игры.
4. **Хуки на горячих методах** (`Update`, `FixedUpdate`, `AbilityStatApply`) — только лёгкие; метки в `Crash` ставятся ядром.
5. **Ничего не ломать в сохранениях.** Не писать в массивы, которые игра сохраняет (`Array_AbilityClassPractice`, золото, самоцветы): контрольная сумма сбрасывает прогресс.
6. **Мод — это zip** (`mod.json` + DLL). Один мод — одна папка в `modkit/melon/mods` (библиотеки, большие) или `examples` (демо). Общие типы живут в `ModKit.dll` или в библиотеке с `"library": true`.

## 3. Фазы и моды

Порядок — от самых безопасных к самым рискованным. Каждый мод: цель, опора (API), критерий готовности, риск.

### Фаза A. Контент из готовых деталей (низкий риск)
**A1. `artifact_pack` — 12 новых артефактов и 2 синергии.** Опора: `AddArtifacts`, эффекты из EFFECTS.md, `CloneFrom` для иконки/редкости, свои иконки через `IconFile`/PNG в zip (по желанию). Темы: «огонь», «лёд», «сбор», «крит», «танк». Каждому — описание на русском, вес выпадения 3–5, редкости C…S. Критерий: после запуска `autotest` с `auto_artifact` (ID нового артефакта) в `gamelog` видны `UnitApply_*` с ожидаемыми значениями; плитки видны в энциклопедии. Риск: иконки образца у всех; пулы выпадения не проверены на редкости.
**A2. `spell_tuner` — пресеты правки заклинаний.** Опора: `EditSpell/ScaleSpell`, `Pager`, `OpenNumberForm`. Экран «Настройка заклинаний»: страницы по 21 заклинанию, поля «урон ×», «КД ×», «число +N» (по ID эффектов из EFFECTS.md) и 3 пресета («Лёгкий», «Обычный», «Хардкор»). Критерий: `modkit.log` показывает изменённые слоты; после перезапуска значения читаются обратно через `GetSpell`; откат при выключении. Риск: текст строк уровней (`효과 설명줄06`) не обновляется — это нужно добавить в `modkit_data` отдельным шагом (файл Spells.cs в `modkit_data`; пометить версию 1.4).
**A3. `class_pack` v2 — 8 классов мода.** Опора: реестр `classes`/`CustomClass`, `SetGlobalEffects`. Темы по школам игры (огонь, лёд, спутники, духи, молния, крит, сбор, танк). Эффекты только статовые (из EFFECTS.md). Критерий: после выбора в `class_menu` лог содержит «класс мода «…»: эффектов N», а значения `UnitApply_*` в бою совпадают с расчётом (см. gamelog). Риск: `GameSprite` портретов классов в `class_menu` не проверен; иконки классов мода по умолчанию — квадратики.

### Фаза B. Активные заклинания (средний риск)
**B1. `active_pack` — ручной каст для всех заклинаний, у которых есть `Play_X`.** Опора: `ISpells.AddActive`, таблица имён в `Spells.cs`. Сначала проверить `CanCast` и пробный `Cast` для каждого из 17 заклинаний таблицы (в `autotest`-режиме: выдать заклинание, нажать), составить таблицу «работает/падает/нет цели». Мод даёт настройку «какие заклинания сделать активными» (Checklist) и кнопки в ряд (до 4 слотов, `Slot`). Критерий: таблица результатов в docs (`ACTIVE_SPELLS.md`, раздел «проверка»), мод включается без ошибок. Риск: часть заклинаний не имеет `Play_X` (CanCast=false), комбо-версии корутин не глушатся.
**B2. `ultimate_button`** — исследовать ультимейты игры (`V_UltimateShow`, `Button_Ultimate_*`, `List_ApplyUltimateON`): можно ли вызвать ультимейт по кнопке, не дожидаясь игровой логики. Только разведка + проба; результат в docs.

### Фаза C. Прогрессия и вызовы
**C1. `achievements` — «достижения» на карте.** Опора: `PanView` (узлы, связи, состояния), события `enemyDeath`, `bossSpawn`, `battleEnd`, `areaChange`, `HudButton` для тоста. Дерево из 15–20 достижений («100 убийств», «Первый босс», «Пережить 10 минут»…) со связями; прогресс хранится в настройках мода (числа) или в файле рядом с `config.json` (JSON, свой). Награды: `SetGlobalEffects` — маленькие постоянные бонусы. Критерий: прогресс виден между запусками, лог пишет «достижение X получено». Риск: не все события проверены; нужно сверить `enemyDeath` и `bossSpawn` по логу.
**C2. `kill_streak`** — серия убийств: на `enemyDeath` счётчик, за каждые N убийств временный бонус (`SetGlobalEffects` на 5–10 с), индикатор на `HudButton`-метке. Критерий: лог «серия N → бонус», спад бонуса по таймеру на игровом времени (пауза — не тикает, см. `ISpells.Paused`).
**C3. `difficulty`** — слайдеры «здоровье врагов ×», «число врагов ×», «шанс боссов» (поля менеджера боя/`Dictionary_AreaEnemyID`, `BattleUnitEnemy`). Сначала разведка полей по `game.cs` и gamelog; если безопасных полей нет — отчёт «невозможно» без кода.

### Фаза D. Локации (самая рискованная)
**D1. Разведка «локации как данные».** `Dictionary_AreaEnemyID`, `areaChange`, `Play_Weather_AreaNN`, как меняются фон/враги после боссов (Виртуальная экосистема, Терра, Глубинная зона). Результат — `docs/AREAS.md`: что читает фон, враги, погоду; какие индексы жёстко заданы; что можно подменить из мода (картинка фона через `RawImage`?, список врагов, музыка). Кода мода — только пробный `area_probe`, пишущий в лог события смены зоны.
**D2. `area_tweaks`** — если разведка D1 положительна: замена списка врагов зоны и погоды настройками.

### Фаза E. Инструменты и качество
**E1. `modkit_data` 1.4**: обновление текста уровней заклинаний при `EditSpell`; `ClassDef` пометить «экспериментально» в XML-комментарии и в доках.
**E2. `autotest` сценарии**: добавить в `tools/autotest.py` сценарий «проверка мода» (включить мод, пройти бой 3 минуты, снять `gamelog`, сравнить поля героя с ожидаемыми значениями из JSON-описания теста). Тест-описание рядом с каждым модом (`<мод>/test.json`).
**E3. Документация**: на каждый мод — раздел в MELONLOADER.md (что делает, как включить, что проверено).

## 4. Как работает агент и что он НЕ делает
- Работает в `D:\Projects\frida\modkit\melon` и `docs`: создаёт новые папки модов, файлы документации; в существующие файлы ядра (`melon\ModKit\*.cs`) **не вносит правки**. Если нужно расширение ядра — записывает запрос в `modkit/docs/API_WISHLIST.md` (что, зачем, предлагаемая сигнатура) и пропускает мод. Исключение — `modkit_data` (E1) можно править.
- Сборка: `python modkit\melon\pack_mod.py <имя>` (ядро собрано: если ругается на отсутствие `ModKit.dll`, собрать `dotnet build -c Release` в `modkit\melon\ModKit`).
- Может заливать **zip-файлы модов** в `/sdcard/Download/ModKit/` через adb (путь adb: `$LOCALAPPDATA/Android/Sdk/platform-tools/adb.exe`, из Git Bash `export MSYS_NO_PATHCONV=1`). Не запускает игру, не заливает `ModKit.dll`, не удаляет файлы на телефоне.
- В git ничего не коммитит. Каждый мод — отчёт: что собрано, что проверено только компилятором, что требует проверки пользователем и как.

## 5. Цикл улучшения
1. Агент собирает мод → кладёт zip и список «что проверить» в отчёт.
2. Пользователь ставит через «+», подтверждает перезапуск плашкой, тестирует.
3. Основной ассистент читает `modkit.log`/`gamelog`, правит мод, повышает версию.
4. После подтверждения мод попадает в раздел «Проверено» MELONLOADER.md; непроверенное остаётся помеченным.
