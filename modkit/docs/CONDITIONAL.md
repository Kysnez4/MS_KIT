# Условные эффекты

Итог разведки (октябрь 2026): как в игре устроены условные, событийные и активные эффекты и как делать свои. Всё ниже проверено в бою, кроме мест, помеченных **не проверено**.

## Коротко

* Обычные характеристики (атака, HP, КД…) — пары `효과ID_NN` в строках таблиц; движок `effects.ts` подставляет их перед `AbilityStatApply` (`ctx.data.setEffects`). **Условные эффекты так не включаются**: ID эффекта в слоте класса, синергии, комбинации или исследования ничего не даёт (проба 67 ID, `effectscan` режим 0: из них поля изменили только 84, 99, 147 и 122).
* Игра обрабатывает условные эффекты **только у артефактов, лежащих в `Z_Database.List_ArtifactObtain`**. Тогда пересчёт (`AbilityStatApply`) пишет параметры в статические переменные `Z_Database.AllyUnitVar_*` (таблица ниже), а логику (счёт убийств, перезарядки, срабатывания) выполняет сама игра.
* Свой условный эффект можно сделать **без артефакта**, тремя способами (ниже). Рабочие примеры: мод `huntertest` (Охотник без артефакта) и мод `rune_defence` (руна защиты при HP < порога).

## Три способа сделать свой условный эффект

### 1. Условие своё, действие — метод игры (проще всего)

Мод сам проверяет условие и вызывает готовый метод героя `C_Battle_AllyUnit`. Пример — `src/mods/rune_defence.ts`: «HP < 15% → руна защиты».

```ts
ctx.before("C_Battle_Manager", "Update", 0, bm => {
    if (++tick % 15 !== 0) return;                               // ~4 раза в секунду
    const hero = findHero(bm);                                   // см. функцию в rune_defence.ts
    const hp = Number(hero.field<number>("Unit_RemainHpRatio").value);   // 0..1
    if (hp < 0.15 && cooldownPassed) hero.method("Unit_Rune_DefenceDivine", 0).invoke();
});
```

Проверено: `Unit_Rune_DefenceDivine()` ставит `DivineTime` = `ApplyRuneTime_Defence` (10,8 с у героя с исследованиями), `IsDivine` = 1. Перезарядку в моде считаем сами (в `rune_defence` — с конца руны: ждём `DivineTime ≤ 0`).

Подходящие методы героя (есть в `game.cs`, **кроме Unit_Rune_DefenceDivine не проверены**): `Unit_AbilityDivine`, `Unit_ShieldDivine`, `Unit_ShieldChargeDivine`, `Unit_AriseDivine`, `Unit_HpBallDivine`, `Unit_DamageDivine`, `Start_Rune_Attack`, `Start_Rune_Obtain`, `Start_Rune_Clear`.

### 2. Параметры эффекта игры: `AllyUnitVar_*` + поля героя (игра ведёт логику)

Так сделан Охотник без артефакта (`src/mods/huntertest.ts`): даём игре параметры, а убийства считает и бонус начисляет она.

1. После каждого `AbilityStatApply` (`Interceptor.attach(..., { onLeave })`) записать переменную: `Z_Database.AllyUnitVar_PowerKillCondition = 100`.
2. Игра при пересчёте сбрасывает статики героя в «выкл.» (`ApplyPowerKillCondition = 9999999`, `ApplyPowerKillInc = 0`) и сама их не восстанавливает, поэтому их держит мод (раз в ~10 кадров в `C_Battle_Manager.Update`): `ApplyPowerKillCondition = 100`, `ApplyPowerKillInc = 1`.
3. Дальше игра сама: `ApplyPowerKillNum` считает убийства, на 100-м обнуляется, `ApplyPowerKillSum` += 1 (+1% атаки), потолок 25%.

Проверено: `Num` растёт, на 100-м убийстве сбрасывается и `Sum = 1`, после пересчётов значения держатся. **Не проверено:** рост атаки в окне характеристик при `Sum > 0`.

Для других эффектов набор «переменная + поля героя» нужно определить так же (снять поля до/после, см. `effectscan`); таблица переменных — ниже.

### 3. Артефакт-якорь (**не проверено**)

Скрытый артефакт, всегда лежащий в `List_ArtifactObtain`; в слоты его строки таблицы `Ability` движок подставляет пары `[ID эффекта, значение]`, и игра обрабатывает их как у настоящего артефакта. Идея следует из того, что условные эффекты включаются только у артефактов; на практике не пробовалась.

## Инструменты

* **`effectscan`** (отладка, только в тестовом бою): режим 0 подставляет ID эффектов, режим 1 по очереди выдаёт артефакты (`ARTIFACTS` в файле) и пишет в `modkit.log` строки `[effectscan] артефакт <ID>: <поле>: было -> стало`. Поля героя `C_Battle_AllyUnit` (числовые, до 1000), `Z_Database.AllyUnitVar_*` и статики `V_Ability_Manager`; шум отсекается двумя «пустыми» пробами. Запускается один раз после входа в бой и сбора крупицы маны.
* **`huntertest`** — пример способа 2, **`rune_defence`** — способа 1.

## Грабли

* `V_Ability_Manager` **не имеет `Update`** (ошибка «метод не найден»). Объект менеджера берётся из хука на `V_Ability_Manager.ManaGain` (срабатывает при получении маны) — не через `Il2Cpp.gc.choose` на каждом проходе: обход кучи даёт сильные лаги.
* Хук `ctx.after("C_Battle_Manager", "Update", ...)` (onLeave) **не срабатывает**; используйте `ctx.before` (onEnter). Тяжёлый код в `Update` держите за счётчиком кадров (`++tick % N`).
* Игра сбрасывает статики героя при каждом `AbilityStatApply`, а `AllyUnitVar_*` пересчитывает с нуля — писать нужно **после** пересчёта (onLeave хука `AbilityStatApply`) и повторять запись.
* Статическое поле `V_Ability_Manager.Ability_SelectON` не трогайте: после сканера, который его восстанавливал, ввод в игре «залипал».
* Принудительная остановка игры (`am force-stop`, деплой) помечается в `modkit.log` как «прошлый запуск завершился аварийно» — это не сбой мода, но набор модов при этом откатывается к последнему стабильному.
* Подстановка эффектов (`patchRows`) раньше занимала 35–970 мс на пересчёт; исправлено чтением ячеек через память (`data.ts`), сейчас 17–96 мс. Мод `gamelog` вызывает собственные лаги — держите его выключенным вне съёмки данных.

## Не проверено

* Рост атаки в окне характеристик у Охотника без артефакта при `Sum > 0`.
* Способ 3 (артефакт-якорь).
* Событийные эффекты на убийство (взрыв, мгновенное убийство) и активные с перезарядкой (Зелье здоровья, Пандора…): переменные известны, поля героя и условия включения — нет.
* Как ведёт себя `Unit_Rune_DefenceDivine` по ощущению в бою (неуязвимость или нет): `IsDivine` = 1 и `DivineTime` = 10,8 подтверждены логом.
